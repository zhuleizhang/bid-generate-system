# Ralph Agent Instructions

你是一个在软件项目中工作的自主编码代理。

## 你的任务

1. 阅读 `prd.json` 中的 PRD（与本文件位于同一目录）
2. 阅读 `progress.txt` 中的进度日志（先检查 `Codebase Patterns` 章节）
3. 检查当前是否位于 PRD 中 `branchName` 指定的分支；如果不是，则切换过去或从 `main` 创建该分支
4. 选择 `passes: false` 且**优先级最高**的用户故事
5. 仅实现这一个用户故事
6. 运行质量检查（如 `typecheck`、`lint`、`test`，以项目实际要求为准）
7. 如果发现了可复用模式，更新 `CLAUDE.md` 文件（见下文）
8. 如果检查通过，使用以下提交信息提交**所有**变更：`feat: [Story ID] - [Story Title]`
9. 更新 PRD，将已完成故事的 `passes` 设为 `true`
10. 将本次进展追加到 `progress.txt`

## 进度报告格式

请将内容**追加**到 `progress.txt`（绝不要替换原内容，只能追加）：

```
## [日期/时间] - [Story ID]
- 实现了什么
- 修改了哪些文件
- **供后续迭代参考的经验：**
  - 发现的模式（例如：“这个代码库在 Y 场景中使用 X”）
  - 遇到的坑（例如：“修改 W 时别忘了同步更新 Z”）
  - 有用的上下文（例如：“评审面板位于组件 X 中”）
---
```

“经验”这一部分非常关键，它能帮助后续迭代避免重复犯错，并更快理解代码库。

## 汇总模式

如果你发现了后续迭代应该知道的**可复用模式**，请将其添加到 `progress.txt` 顶部的 `## Codebase Patterns` 章节中（如果不存在就创建）。这个章节应汇总最重要的经验：

```
## Codebase Patterns
- 示例：聚合场景使用 `sql<number>` 模板
- 示例：数据库迁移始终使用 `IF NOT EXISTS`
- 示例：UI 组件需要从 `actions.ts` 导出类型
```

只添加**通用且可复用**的模式，不要写与某个故事强绑定的细节。

## 更新 CLAUDE.md 文件

提交前，检查已编辑文件所在目录附近的 `CLAUDE.md` 是否需要补充值得沉淀的经验：

1. **识别已编辑文件所在目录**：查看你修改了哪些目录
2. **检查是否已有 `CLAUDE.md`**：在这些目录或其父目录中查找 `CLAUDE.md`
3. **补充有价值的经验**：如果你发现了未来开发者或代理应该知道的内容，例如：
    - 该模块特有的 API 模式或约定
    - 容易踩坑的点或不明显的要求
    - 文件之间的依赖关系
    - 该区域的测试方式
    - 配置或环境要求

**适合写入 `CLAUDE.md` 的示例：**

- “修改 X 时，也要同步更新 Y，才能保持一致”
- “这个模块的所有 API 调用都遵循 Z 模式”
- “测试要求开发服务器运行在 3000 端口”
- “字段名必须与模板严格一致”

**不要添加：**

- 某个故事专属的实现细节
- 临时调试笔记
- `progress.txt` 中已经记录过的信息

只有当你获得了**真正可复用**、能帮助该目录后续工作的知识时，才更新 `CLAUDE.md`。

## 质量要求

- 所有提交都必须通过项目的质量检查（`typecheck`、`lint`、`test`）
- 不要提交有问题或不可用的代码
- 保持改动聚焦且尽量最小化
- 遵循现有代码模式

## 浏览器测试（如果可用）

对于任何会改动 UI 的故事，如果你已配置浏览器测试工具（例如通过 MCP），请在浏览器中验证其是否正常工作：

1. 打开相关页面
2. 验证 UI 改动是否符合预期
3. 如果对进度记录有帮助，可以截图

如果没有可用的浏览器工具，请在进度报告中注明：需要人工进行浏览器验证。

## 停止条件

完成一个用户故事后，检查是否所有故事的 `passes` 都为 `true`。

如果所有故事都已完成并通过，请回复：
<promise>COMPLETE</promise>

如果仍有故事的 `passes: false`，则正常结束本次响应（下一轮迭代会继续处理下一个故事）。

## 重要事项

- 每次迭代只处理**一个**故事
- 频繁提交
- 保持 CI 处于通过状态
- 开始前先阅读 `progress.txt` 中的 `Codebase Patterns` 章节

## 代码注释规范

- **语言**：所有注释使用中文。
- **原则**：只注释重要业务逻辑，不注释一眼就能看懂的代码。
- **目标**：让读者快速理解业务意图和决策原因，而不是解释代码语法。
- **需要注释的场景**：
    - 为什么要这样处理（非显而易见的业务规则、边界条件、特殊兼容）
    - 为什么选这个方案而不是另一个（取舍原因）
    - 容易踩坑的地方（Word XML 结构陷阱、表格合并单元格的特殊处理等）
- **不需要注释的场景**：
    - 简单的 getter/setter、CRUD 操作
    - 变量赋值、循环遍历、条件判断等基础语法
    - 函数名和参数名已经自解释的逻辑
- **注释风格**：单行用 `#`（Python）或 `//`（TypeScript），保持简洁，一行说清楚即可。
